# Chat file uploads

Use **＋ Attach** in the Web UI chat composer, or drag files onto the composer. Review the selected filenames, remove unwanted files, enter a message and send. Files are transmitted with that chat submission, not when selected. Definitively rejected submissions preserve the message and selected files. An uncertain response uses the existing operation-reconciliation barrier; it never automatically repeats inference.

Supported inputs are UTF-8 text/code/data (including Markdown, CSV and JSON), searchable and scanned PDFs, Word `.doc`/`.docx`, PNG, JPEG and GIF. Choose up to four files, with an 8 MiB combined original-byte limit. PDF extraction supports up to 40 pages; document/text extraction is limited to 64 KiB per file and 128 KiB combined, and the selected model's existing context limits still apply. Oversized or unreadable content is rejected rather than silently truncated. Encrypted/password-protected documents, spreadsheets in binary formats and other image formats remain unsupported. Scanned/image-bearing PDF pages use local English OCR, including image pages that also contain a searchable header. At most 10 pages may require OCR within the 40-page PDF limit. OCR output is labeled and may contain recognition errors; handwriting, unusual layouts and other languages are not guaranteed. Word extraction includes document-body text/tables; embedded media, headers, comments and visual layout are not interpreted. GIF analysis uses its first frame.

Images require a configured Ollama or OpenAI-compatible model that actually supports vision. Use an explicit model, for example `@local/model-ID`; automatic image routing and unsupported CLI transports are rejected before dispatch. The configured model is pinned without fallback for image requests. Original images are retained, while a JPEG optimized to at most 512 pixels on its longest side (smaller when necessary) and 4 KiB of JPEG bytes is supplied through the provider's real image field. Fine details and orientation metadata may not survive this optimization. Files currently work through the commanding host's normal chat path; direct `@remote-host` delivery with attachments is blocked explicitly rather than dropping the files.

After the chat starts, the **Files** section lists the uploaded originals alongside generated outputs. PNG/JPEG originals support inline previews; all originals can be downloaded with their exact original bytes. Text extracted from user uploads is available in expandable user-message details. Refreshing or reopening the chat reconciles from durable state. Follow-ups inherit the source chat's actual configured model rather than switching to the default coordinator.

## Storage and authority

The existing authenticated, same-origin, CSRF-protected chat submit/resume API accepts an optional `files` array of `{name,data}` with base64-encoded bytes. Only those two actions may carry files. The encoded upload request is bounded to 12 MiB; ordinary non-upload text retains its 1 MiB bound. Filenames are display metadata, never filesystem paths. File contents remain untrusted data and grant no tool permissions. Uploaded scripts, document macros, external relationships and links are not executed.

Originals are stored under the private task-database-adjacent `.chat-inputs` directory before admission, using immutable operation-bound rows. A durable binding to the server-generated request-key digest is recorded before queuing; collection resolves it from a proven task's native submission metadata, not a model-provided path or identifier. The existing `.chat-files` store retains chat-bound download snapshots. Existing payload quotas apply independently to each store (256 MiB per bucket, 512 MiB total original payload per store); these are payload quotas, not a hard bound on SQLite overhead. Unsubmitted/rejected-upload cleanup and a user-facing storage manager remain future work.

PDF parsing uses the pinned [ledongthuc/pdf reader](https://github.com/ledongthuc/pdf) in an owned parser child with a 20-second parent deadline, 18-second internal processing budget, bounded input/output and a 64 MiB Go memory target. The whole attachment preparation stage is limited to 22 seconds. Poppler renders one OCR page at a time to at most 2400 pixels on its longest side (6 MiB raster output bound); Tesseract reads it on stdin, with an eight-second limit per helper. macOS `.doc` uses the built-in textutil importer; Linux uses antiword. Both output plain UTF-8 text, never run Word/macros, and enforce the same text limits. This is process isolation for parsing and cancellation, not an operating-system sandbox or a hard memory limit. The child receives bytes on stdin, not a private filename. Word XML extraction is bounded and never unpacks to the filesystem. Image dimensions are checked before decoding (16 million pixels maximum). License: [PDF dependency notice](third-party/pdf-license.txt). Ollama's wire format follows its [vision documentation](https://docs.ollama.com/capabilities/vision).

## Local OCR and legacy Word readers

On macOS install Tesseract and Poppler (`brew install tesseract poppler`); textutil is built in. On Debian/Ubuntu the corresponding packages are `tesseract-ocr`, `tesseract-ocr-eng`, `poppler-utils` and `antiword`. Runtime discovery only checks the fixed executable directories `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and `/bin`; user-controlled PATH commands are not used. The initial OCR language is English. See [Tesseract CLI documentation](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html) and [Poppler utility documentation](https://manpages.debian.org/trixie/poppler-utils/pdftoppm.1.en.html).

Missing readers, processing timeouts, unreadable/encrypted files and extraction limits fail before inference; they never return a successful partial document. The browser keeps the draft after a definitive rejection so the user can remove files or use fewer pages. Installing a missing helper does not require changing model permissions or enabling automatic tool approval. Original file downloads remain unchanged.

On macOS/Linux the parent owns the entire extraction process group and its 0700 temporary workspace. It kills remaining descendants on cancellation, parser failure and completion, then removes temporary source/raster files. Helpers receive a minimal environment; raster bytes pass directly to OCR rather than being retained as additional files. This is not an OS network sandbox or hard native-memory cap. Other operating systems do not currently have a provisioned OCR/legacy-reader path. Linux ARM64 builds are checked, but installed reader integration is verified on macOS; Linux antiword execution remains an explicit verification gap.

## QA hardening

Searchable text on image-bearing PDF pages is retained separately from OCR output, including when OCR finds no text. DOCX explicit line breaks and tabs are preserved. The 64 KiB/file and 128 KiB combined decoded-content bounds also apply to attachment decoding; the encoded frame has a separate 1 MiB bound so JSON escaping cannot silently invalidate an otherwise legal upload. HTTP upload limits are unchanged.

Credential scrubbing decodes attachment text/name fields before redacting and encoding them again; it never rewrites JPEG base64 as text. Saved inference history retains image inputs for follow-ups. Browser history and the routing classifier receive image metadata/text placeholders instead of unnecessary image base64. Originals remain private, unchanged download snapshots: text redaction is not a claim that original documents or image pixels have been scrubbed. Transparent images are composited onto white for analysis and previewed on white so black content remains legible; their original transparency is preserved in downloads.
